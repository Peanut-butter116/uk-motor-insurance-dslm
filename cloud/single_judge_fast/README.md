# d1000-single-judge-fast-v1

Owner-authorised mixed-provider single-valid-judge evaluation. Original dual-judge code, journals, metrics and calibration records remain historical and unchanged. New valid votes append to provider journals with this protocol's provenance; original strict transport/cache identity is retained because model, prompt, rubric and validators are unchanged.

For each response reuse a strictly validated saved vote. Select Groq deterministically if both historical providers have valid votes; otherwise use the available vote. A shared queue claims only responses without any valid vote, so concurrent providers cannot create new pairs. One worker per provider is used until measured latency and quotas justify more. No agreement analysis is generated.

`handoff.py` drains the old worker after a control-cell interrupt at an independently read-back checkpoint. Python SIGINT interrupts the main thread, not the provider threads; the observed interrupt was in thread.join, outside persistence. The stop gate prevents subsequent old calls; existing calls finish their durable outcome handling. After zero workers remain, final dual checkpoint249 is published and independently verified. The same private lease and local exclusive lock are transitioned, never cleared or recreated.

`engine.prepare` validates all saved votes against their exact task/provider/model cache and unchanged strict schema and semantic validators. Both original nine-case calibrations must verify. Latest results, private lease owner readback, inactive Kaggle writer and immutable artifacts are required. No judge calls occur in preflight. Existing Gemini unknown task/provider histories are excluded from scheduling without editing or replaying them. Other independent Gemini tasks can proceed. New transport-uncertain outcomes stop that provider for the session and remain protected.

`quotas.py` retains all provider ledger entries and original locking, reconciliation, reservations, token counting and 429 pauses. Groq accounting stays unchanged. Gemini RPD uses documented midnight America/Los_Angeles calendar boundaries; RPM/TPM remain rolling60 seconds and configured TPD remains rolling24 hours. DST is handled using zoneinfo. This is a separately documented accounting window, not a ledger reset. Source: https://ai.google.dev/gemini-api/docs/rate-limits . No server remaining quota is invented: reports distinguish conservative local tracked remaining values from unknown external account usage.

The 20-hour clock starts at the new coordinator's launch epoch, recorded with a deadline in private protocol.json. Preflight projects coverage using ledger capacity, documented reset times, historical actual token use and current prompt estimates. Projections do not guarantee successful calls. Requests use original strict reservation rules; no prompt truncation or cheaper models. New calls stop15 minutes before the deadline to drain and persist. A STOP_REQUESTED file allows cooperative shutdown. One primary private Kaggle store remains authoritative.

Checkpoints pause new claims, drain active calls, compute separate deterministic and selected-vote metrics, then publish and read back the archive with the existing guarded checkpoint implementation. Actual archive vote counts must match the snapshot. Five new unique successes or five minutes trigger persistence. Each report includes unique coverage, missing responses, provider vote totals, measured unique successes/hour, quota-aware estimated hours, limits/remaining ledgers/reset epochs and protected request counts. No missing vote is scored zero. All available model/condition denominators remain76; DeepSeek stays N/A.

Private outputs: results_single_judge_fast_v1/comparison.json, comparison.csv, selected_votes.json; single_judge_fast_v1/protocol.json, progress.json, new_assignments.jsonl and safe_failures.jsonl. Never publish selected-vote IDs, raw journals, provider requests, model outputs or archives. Only aggregate summaries may enter GitHub.

## HTTP503 quarantine continuation

After the second Gemini HTTP503, the owner authorised response-level quarantine across both providers. `eligible_tasks` excludes the union of all protected unknown response IDs from both queues. Existing valid votes remain selected; an unknown task is neither replayed nor reassigned to the other judge. Strict original request handling is unchanged. A new transport-uncertain failure still stops that provider for the session rather than repeatedly probing an outage with research calls.

`continuation.resume_same_runtime` requires a deliberately drained, independently read-back suspension, zero provider tasks/threads, unchanged lease and original deadline. It revalidates votes, calibrations, model availability, hashes and latest storage/lease state. Every existing journal/cache/quota file is hash-checked across preflight. The stop marker is archived only after these checks. Flags, leases, reservations and original launch time are never reset. A successful catalogue GET verifies model availability but does not prove generation service health; actual new validated, persisted judgements are required before reporting successful recovery.

Both observed HTTP503 requests lack durable raw replies, so they remain unresolved. This can limit complete coverage even when independent work succeeds. Google documents503 as service unavailable, not evidence that a request was never processed: https://ai.google.dev/gemini-api/docs/troubleshooting . No automatic replay is introduced.

## Supported runtime renewal

Free Colab cannot guarantee a continuous20-hour VM. `lifecycle.suspend` is for a controlled safe stop: signal STOP_REQUESTED, wait for all named provider tasks and actual completion-thread stacks to drain, strictly recover any fully validated cached success missing its journal row, then independently publish/read back the final snapshot. It records an explicit suspension proof and unchanged original deadline. It must be invoked only after the active control cell has exited; it does not kill requests.

`resume.restore` accepts only a fresh private CPU VM and a latest production checkpoint explicitly marked as a fully drained suspension. It pulls exact original18 code, verifies the latest archive/912 responses/3 adapters/benchmark, validates all saved votes and protected histories, verifies the previous lease owner, runs a fresh private scratch readback, then versions the existing private lease to the new session. The new coordinator preserves the original launch time, baseline and20-hour deadline. No quota entries, caches, unknown histories or votes are reset. A live old writer, nonsuspended checkpoint, expired deadline or changed lease blocks restoration. A generic lost VM with possible unsaved requests is not eligible for automatic replay or this supported renewal path.

A runtime restart remains an operational dependency, not proof that resources will be available. Never run the old checkpoint239 preflight over a newer checkpoint. Do not rerun all notebook cells. Use the reviewed renewal entry only after a controlled suspended checkpoint has passed readback and the previous coordinator is definitively stopped.

## Reconciliation of a provably idle lost VM

`idle_loss.validate` adds a separately audited case; arbitrary VM loss remains blocked. It requires independent confirmation that the old VM ended, the latest private readback, zero active provider calls, and exact reviewed engine/protocol hashes. The durable snapshot must show Gemini's worker already stopped and Groq quota-waiting beyond the original deadline. In that exact worker implementation no later request is possible. A merely quota-paused Gemini worker, an earlier Groq reset, active call, unknown source revision or changed lease fails closed.

Only after archive/input/journal validation, old lease-owner verification and a fresh scratch private readback may the new CPU VM version the same lease. The private reconciliation audit records why post-checkpoint requests were impossible; it does not change unknown statuses or claim the old VM was deliberately suspended. All unknown responses remain quarantined across providers. The original20-hour clock is retained. The notebook's default restore still requires controlled suspension; the idle-loss entry must be selected only after the separate runtime-termination and source/state evidence is verified.

On a fresh VM, Colab userdata configures the three existing credentials before importing the SDK, whose import can attempt authentication. Credential values are never printed or stored in source/artifacts. This acquisition-order repair does not alter storage access controls.
